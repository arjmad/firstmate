This supersedes the home-file source in the [2026-11-11 worker-denied MCP servers record](2026-11-11-worker-denied-mcp-servers.md), whose denial mechanism stays.
Why: the two lists had drifted, because the fleet repository dropped `monarch` from its rendered list on 2026-11-19 while a home's plain-file copy still named it, so lifting one denial took two changes in two repositories.
Decision: every Claude ship and scout spawn and relaunch reads the rendered file, which `FM_WORKER_DENIED_MCP_SERVERS_FILE` can override, and no longer reads or inherits the home file; homes may remove their copy.
A missing, unreadable, or malformed rendered file denies the worker every MCP server through `"allowedMcpServers":[]` in its inline `--settings` JSON and prints a warning naming the file, rather than refusing the spawn, so a host that does not render the list keeps dispatching Claude workers without MCP servers instead of stopping all Claude dispatch.
Live check on Claude Code 2.1.325: `claude -p --settings '{"allowedMcpServers":[]}'` blocked a `--mcp-config` stdio server ("MCP server blocked by enterprise policy") and loaded none of the user-scope servers (`exa`, `firecrawl`, `gbrain`, `monarch`) the same launch loads with `--settings '{}'`.
No upstream proposal: the rendered list is this fleet's account layout.
